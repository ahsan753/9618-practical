How this lesson works

Six lessons taught you to build classes in Python. This one closes the three gaps that are left — two that Paper 3 tests on paper, and one that Paper 4 keeps setting.

  1. Part A — on paper. Paper 3 asks for classes in Cambridge pseudocode and as class diagrams, never in Python. You will translate the Member class you already know, then do two real Paper 3 questions with their mark schemes.
  2. Part B — in Python. Predict, run, investigate, modify: sorting an array of objects, and writing output that depends on which class an object belongs to.
  3. Evidence it. Section A of the Evidence Document is typed pseudocode. Section B is your code pasted as text plus a screenshot. Submit the one document on Teams.

The three gaps this lesson closes

1. A class in pseudocode. CLASS … ENDCLASS, PRIVATE declarations, a constructor called NEW. Recent Paper 3s ask for it directly — June 2026 paper 32 gave five marks for nothing else.

2. A class diagram with getters and setters. Paper 3 asked for one in November 2024 and again in two variants of June 2025. The November 2024 examiners reported that marks higher than three out of five were rare, because setters were written without a parameter and its data type.

3. Sorting objects, and output that depends on the class. Sorting is in almost every Paper 4. When the data is held in objects, you compare one field and move the whole object. And when a design says "if it is a helicopter, also output…", the June 2023 examiners found that most candidates simply output everything for every object.

What pseudocode leaves out — and what it adds

There is no self and no __: inside the class, an attribute is just its name. In exchange, everything has a data type — every attribute, every parameter, and every function's RETURNS. A Python habit of leaving types in comments becomes, in pseudocode, a mark you lose if the type is missing.

The five rules the mark schemes check

  1. CLASS name … ENDCLASS. A mark of its own in both questions you will see today. Forgetting ENDCLASS loses it.
  2. The attributes are declared first, before the constructor, each one PRIVATE Name : TYPE. The June 2026 mark scheme gives this a mark: "correct attribute declaration section before the constructor".
  3. The constructor is PUBLIC PROCEDURE NEW(…) … ENDPROCEDURE — a procedure, because it returns nothing. Every parameter has a name and a type.
  4. A parameter must not have the same name as its attribute. In Python self.__Name = Name works, because self. tells them apart. In pseudocode Name ← Name means nothing. The June 2026 mark scheme says the parameters can have "any names … except" the attributes' names, and the June 2025 examiners repeated it for setters. Use GivenName, NewName, CarMake — anything else.
  5. Attribute on the left of the arrow. Name ← GivenName stores the parameter. GivenName ← Name throws it away. Fixed values such as Credits ← 0 are assigned in NEW, not passed in.

A child class adds INHERITS to the header and calls SUPER.NEW(…) as the first line of its constructor — exactly Lesson 5's super().__init__(…):

Pseudocode — Paper 3 
CLASS JuniorMember INHERITS Member
   PRIVATE GuardianName : STRING
   PRIVATE ConsentGiven : BOOLEAN

                        GivenGuardian : STRING)
      SUPER.NEW(GivenID, GivenName, GivenAge)
      GuardianName ← GivenGuardian
      ConsentGiven ← FALSE
   ENDPROCEDURE
ENDCLASS

Checkpoint 1

A class Book has the private attributes Title : STRING and Pages : INTEGER. Its constructor takes both values as parameters. Which constructor would earn every mark?

This is the Python habit carried across. With no self. to tell them apart, Title ← Title assigns a name to itself and the attribute is never set. Cambridge's June 2026 mark scheme allows "any names … except" the attribute names for the parameters, so the parameter mark and the assignment mark both go.
The names are fine — but the arrows point the wrong way. NewTitle ← Title copies the (empty) attribute into the parameter and then throws it away. The attribute always goes on the left: it is the thing being given a value.
Parameters with their own names and types, and each attribute on the left of its arrow. Notice that no RETURN appears anywhere: a constructor sets up the object and hands nothing back.
A constructor is a procedure, PUBLIC PROCEDURE NEW. Creating the object is done by NEW Book(…) in the calling code, not by a return value — the mark scheme's "begin and end the constructor as PUBLIC PROCEDURE NEW … ENDPROCEDURE" is lost.

Checkpoint 2

Still in Book. Which is the getter for Pages?

Lesson 2's trap in a new language. A getter returns the value to whatever called it; OUTPUT only displays it, and the caller gets nothing back to store or compare. And something that returns a value is a FUNCTION, not a PROCEDURE.
The single most repeated OOP error in the Paper 4 reports — a parameter on a getter — and it is just as wrong on paper. A getter needs nothing from the caller. Worse, the parameter is called Pages, so RETURN Pages would return the caller's value, not the attribute.
Close — but Pages is an INTEGER, so the function must say RETURNS INTEGER. The data type in RETURNS has to match the attribute it hands back.
A function, no parameter, the right return type, and one RETURN of the attribute unchanged. This is the template for every getter on Paper 3.

Class diagrams — the names are already on the page

Choosing the data type

Decide from what the value is, and check it against anything already printed. A telephone number such as 01223658721 is a STRING: it starts with a zero and you never do arithmetic with it. Checkpoint 3

A hotel's class diagram for Booking already shows the setter SetRoomNo(NewRoom : INTEGER) and the getter GetRoomNo(). Rooms are identified by a 4-digit number, for example 2105. Which attribute line earns the mark?

A sound rule of thumb on its own — but the diagram has already decided: the setter takes an INTEGER and stores it in this attribute, so the attribute must be an INTEGER too. In the June 2025 question on this page, Cambridge's mark scheme printed PatientID : INTEGER for exactly this reason.
The parameter is not the attribute. The attribute's name comes from the method's name — SetRoomNo sets RoomNo — and the parameter deliberately has a different name, which is what the examiners said they expect.
Clearer, perhaps, but inconsistent: SetRoomNo and GetRoomNo are already printed, so the attribute they set and return is RoomNo. "Inconsistency of naming across the various parts of the question" is the first error the June 2025 examiners named.
The name comes from SetRoomNo and GetRoomNo, and the type comes from the setter's parameter. Both agree with what is already printed, which is what the marks reward.

class Player:
    def __init__(self, Name, Score):

Players = [None] * 6                  # ARRAY[0:5] OF Player
Players[0] = Player("Kai", 31)
Players[1] = Player("Mia", 58)

for Pass in range(0, Count - 1):

PRIMM · Step 3

Investigate — sorting objects, and output by class

1. The anatomy of a bubble sort on objects

# 1. only the slots in use
for Pass in range(0, Count - 1):
    for Index in range(0, Count - 1 - Pass):
        # 2. compare a FIELD, through the getters
        if Players[Index].GetScore() > Players[Index + 1].GetScore():
            # 3. swap the WHOLE object, with a temporary variable
            Temp = Players[Index]
            Players[Index] = Players[Index + 1]
            Players[Index + 1] = Temp
  1. Only the slots in use. The loops run up to the number of objects actually stored — Count here, NumberOfMembers in the club. Each pass pushes the largest remaining value to the end, so the inner loop can stop one place earlier each time (- Pass).
  2. Compare a field, through its getter. GetScore() on both objects. The attribute is private, so Players[Index].__Score is not an option — and comparing the objects themselves is a TypeError.
  3. Swap the whole object, with a temporary variable. Three lines, every time. The object carries all its attributes with it, so nothing can be left behind.

Why this matters on Paper 4 — partial swaps

When the same data is held in a 2D array or in parallel arrays, every field has to be swapped separately, and candidates forget some. November 2024, paper 42: "a common error was only swapping the index that was being used in the comparison, for example the game level was swapped for two of the players but not the score and player ID." Objects remove that risk — as long as you swap the object, not a field.

Checkpoint 4

Players have the methods GetName(), GetScore() and SetScore(). Inside the sort, the comparison has decided that two players must change places:

if Players[Index].GetScore() > Players[Index + 1].GetScore():
    # swap — which code goes here?
It runs, and the scores come out in order — which is why it is dangerous. The scores have moved but the names have not, so Mia ends up holding Zane's score. This is the partial swap from the examiner reports, done with setters: one field moved, the rest left behind.
No temporary variable. The first line overwrites slot Index, so by the second line the original object is gone and both slots hold the same player. One player is duplicated, the other is lost.
The object in slot Index is kept safe in Temp, the other object moves down, and Temp fills the gap. Whole objects move, so every attribute stays with its owner.
Nearly the right shape, but Temp saves the wrong slot. Temp holds the object from Index + 1, and the last line puts that same object back where it came from — both slots end up with the same player. Save the slot you are about to overwrite.

2. Output that depends on the class

Sometimes a design says: "outputs the name and score; if the player is a pro, also outputs the sponsor". Cambridge accepted three designs for exactly this in June 2023 (paper 41, Q2(c)): a method in each class that overrides the parent's (Lesson 5), testing the object's type, or exception handling. Testing the type is the most direct, and in Python it is isinstance(Object, ClassName).

class ProPlayer(Player):
    def __init__(self, Name, Score, Sponsor):
        super().__init__(Name, Score)
        self.__Sponsor = Sponsor      # STRING

    def GetSponsor(self):
        return self.__Sponsor

def ShowPlayer(ThePlayer):
    print(ThePlayer.GetName() + " scored " + str(ThePlayer.GetScore()))
    if isinstance(ThePlayer, ProPlayer):
        print("Sponsor: " + ThePlayer.GetSponsor())

isinstance(ThePlayer, ProPlayer) is True only when the object belongs to ProPlayer (or a child of it). For an ordinary player it is False, and the sponsor line is skipped — which matters, because an ordinary player has no GetSponsor() and would crash.

Checkpoint 5

ProPlayer is a child of Player. The array Squad holds one ordinary player, Kai, and one pro, Ravi. What does this loop output for Ravi?

for Item in Squad:
    if isinstance(Item, Player):
        print(Item.GetName() + " (player)")
    elif isinstance(Item, ProPlayer):
        print(Item.GetName() + " (pro)")
This is what the programmer meant, and it is not what happens. A pro is a player — that is what inheritance means — so the very first test, isinstance(Item, Player), is already True for Ravi. The elif is never reached, for anyone.
Inheritance cuts both ways: a ProPlayer object is also a Player, so the first test succeeds and the elif never runs. Test the child class first — or test only the child, and let else handle everything else.
An if … elif runs at most one branch. Once the first condition is True, the rest are skipped — so even though Ravi passes both tests, only one line is printed.
isinstance accepts the object's own class or any parent of it — that is precisely why it is useful, and why the order of the tests matters. There is no error.

The marks · a real Paper 4 question

Exam technique — "if it is a helicopter, also…"

June 2023, paper 41, Question 2. The class Vehicle has getters including GetHorizontalPosition() and GetCurrentSpeed(). The child class Helicopter inherits from Vehicle and adds a vertical position, with its own getter GetVerticalPosition().

A procedure needs to output the horizontal position and speed of a vehicle. If the vehicle is a helicopter, it also outputs the vertical position. All outputs must include appropriate messages. Write program code for this procedure.

class Member:
    def __init__(self, MemberID, Name, Age):
        self.__MemberID = MemberID   # STRING
        self.__Name = Name           # STRING
        self.__Age = Age             # INTEGER
        self.__Credits = 0           # INTEGER
        self.__Active = True         # BOOLEAN

    def DisplayDetails(self):
        print("Member ID : " + self.__MemberID)
        print("Name      : " + self.__Name)
        print("Age       : " + str(self.__Age))
        print("Credits   : " + str(self.__Credits))
        print("Active    : " + str(self.__Active))

    def GetName(self):
        return self.__Name

    def GetCredits(self):
        return self.__Credits

    def SetAge(self, NewAge):
        self.__Age = NewAge

    def AddCredits(self, Amount):
        NewTotal = self.__Credits + Amount
        if NewTotal > 50:
            NewTotal = 50
        self.__Credits = NewTotal

class JuniorMember(Member):
    def __init__(self, MemberID, Name, Age, GuardianName):
        super().__init__(MemberID, Name, Age)
        self.__GuardianName = GuardianName       # STRING
        self.__ConsentGiven = False              # BOOLEAN

    def SetConsentGiven(self, NewConsent):
        self.__ConsentGiven = NewConsent

    def DisplayDetails(self):
        super().DisplayDetails()
        print("Guardian  : " + self.__GuardianName)
        print("Consent   : " + str(self.__ConsentGiven))

    def AddCredits(self, Amount):
        if self.__ConsentGiven == False:
            print(self.GetName() + " needs consent before earning credits")
        else:
            super().AddCredits(Amount)

class Club:
    def __init__(self, ClubName):
        self.__ClubName = ClubName          # STRING
        self.__Members = [None] * 5         # ARRAY[0:4] OF Member
        self.__NumberOfMembers = 0          # INTEGER

    def AddMember(self, NewMember):
        if self.__NumberOfMembers < 5:
            self.__Members[self.__NumberOfMembers] = NewMember
            self.__NumberOfMembers = self.__NumberOfMembers + 1
            return True
        else:
            return False

Accepted alternatives

  • MP1: an outer loop that repeats a fixed NumberOfMembers - 1 times, or a while loop with a swapped flag; the inner loop may run to NumberOfMembers - 1 without - Pass.
  • MP6: type(Item) == JuniorMember. Or Cambridge's other accepted design — a method in each class that returns or outputs the line, with JuniorMember's version overriding Member's — provided DisplayAll() calls it.

Not credited, however good the code looks

  • sort(), sorted() or any in-built sort — MP1 to MP4 lost. The design asks for a bubble sort.
  • Comparing the objects themselves, self.__Members[Index] < … — MP2 lost, and it is a TypeError.
  • Swapping only the credits — MP4 lost. It is a partial swap; the names stay where they were.
  • Testing isinstance(Item, Member) — MP7 lost. Every member, junior or not, would be marked junior.
