The two traps this lesson is about

1. Not calling the parent's constructor. A child class must pass the parent's parameters up to the parent's constructor. That call is a separate mark in almost every Paper 4 inheritance question, and in June 2025 examiners named the parent-constructor call a national weakness.

2. Reaching into the parent's private attributes. A child class inherits the parent's attributes, but its code cannot use them by name. In Python, self.__Name inside the child crashes. You go through the parent's methods instead — and once you see why, it stops being a surprise.

Key terms — learn these wordings

TermDefinition that earns the mark
InheritanceThe capability of defining a new class that has all the attributes and methods of a parent class. The methods and properties of the parent (base) class are made available to, and reused by, the child (derived) class.

super().__init__		The first line of a child's constructor. It passes the parent's parameters to the parent's constructor, which sets the parent's attributes for this object.

How definitions lose the mark

"Inheritance is when a class inherits from another class" scores nothing — it uses the word to define itself. Examiners have rejected exactly this (November 2022). Say what the child class gets: all the attributes and methods of the parent. And for polymorphism, "a method with many forms" is a translation of the Greek, not a definition. Say what happens: the same method behaves differently depending on the class of the object.

PRIMM · Step 3

Investigate — how a child class is built

1. The anatomy of a child class

class Novel(Book):                              # 1. the parent goes in the brackets
    def __init__(self, Title, Pages, Genre):    # 2. the parent's parameters, then its own
        super().__init__(Title, Pages)          # 3. the parent's constructor sets Title and Pages
        self.__Genre = Genre                    # 4. only the child's own attribute — STRING
  1. The parent goes in the brackets. class Novel(Book): — a novel is a book.
  2. The constructor takes everything a Book needs, plus what a Novel adds. Here that is Title and Pages for the parent, and Genre for the child. Follow the order the design gives.
  3. The first line passes the parent's parameters up. super().__init__(Title, Pages) runs Book's constructor for this object. Book.__init__(self, Title, Pages) is also accepted — note that this form needs self.
  4. Then only the child's own attributes. Never re-declare Title or Pages in the child. The parent already has them, and copies made in the child are different attributes that the parent's methods cannot see.

Checkpoint 1

The parent class Car has the constructor __init__(self, Make, Model, Price). The design says: "ElectricCar is a subclass of Car. Its constructor takes the make, model and price, and the battery range, BatteryRange : INTEGER." Which constructor follows the design?

The child's constructor has to receive the parent's parameters before it can pass them on. Here the parent's constructor is called with nothing, so Python stops: TypeError: Car.__init__() missing 3 required positional arguments.
The tempting one — it runs without an error. But it never calls the parent's constructor, so it loses that mark, and the four attributes it creates belong to ElectricCar, not to Car. The first time a Car method such as GetMake() is used on an electric car, it crashes: 'ElectricCar' object has no attribute '_Car__Make'.
The parent's three parameters, then the child's own. The parent's constructor sets the make, model and price; the child stores only what it adds. This is the shape of every child constructor you will write.
Car's constructor takes three values, not four, so Python stops: TypeError: Car.__init__() takes 4 positional arguments but 5 were given (it counts self). The battery range belongs to the child, so the child stores it itself.

2. Private means private — even to the child

Every Novel object really does hold a title: the parent's constructor put it there. But the title is private to Book, the class that declared it. Code written inside Novel is not code written inside Book, so it has to ask, exactly as the main program does.

Inside a Novel method you writeWhat happens
self.GetTitle()✓ Returns the title. GetTitle is inherited from Book, and Book's own code is allowed to read __Title.
self.__Title✗ AttributeError: 'Novel' object has no attribute '_Novel__Title'. Python renames a private attribute after the class it is written in, so inside Novel it looks for a Novel title — and there isn't one.

Do not take Python's hint

Python sometimes adds Did you mean: '_Book__Title'? to that error. Typing self._Book__Title would work — and it is reaching round the privacy that earned you the attribute marks in the first place. This is not a Python quirk, either: Private in VB.NET and private in Java hide the attribute from the child class in just the same way. The child uses the parent's methods.

Checkpoint 2

You add a method to Novel that outputs, for example, Dune is a novel. Which line works and respects the design?

Inside Novel, Python reads self.__Title as self._Novel__Title. The title was stored by Book as _Book__Title, so this crashes with an AttributeError. Private means private to the class that declared it.
A good instinct — "the title belongs to the parent, so ask the parent" — but super() gives you the parent's methods, not its private attributes. Python still renames __Title to _Novel__Title and crashes: 'super' object has no attribute '_Novel__Title'.
GetTitle is inherited from Book, so every novel has it, and it is Book's own code that reads the private attribute. The child goes through the parent's methods, not round them.
This asks the class Book for a title, not this particular novel — and the class itself has no title, only its objects do. It also hits the private renaming, so it crashes with an AttributeError.

3. Overriding — replace, or extend

A child overrides a method by defining one with the same identifier. There are two ways to write the new version, and Cambridge credits both — the mark schemes accept "overriding / overloading / extending / using the parent method".

WayLooks likeUse it when
Extenddef Describe(self):
    super().Describe()
    print("Genre: " + self.__Genre)		The child does everything the parent does, and more. Almost always the right choice in Paper 4 — and it reuses the parent's output without retyping it.
Replacedef Describe(self):
    print("A novel: " + self.GetTitle())		The child behaves differently and does not need the parent's version at all.

Polymorphism is what you saw in the loop: one call, Item.Describe(), and Python runs the version that belongs to the object's own class. Python and Java need no keyword to override. VB.NET does — Overridable on the parent's method and Overrides on the child's.

Checkpoint 3

The class Mix is a child of Yarn. It overrides YarnInfo() like this:

    def YarnInfo(self):                     # inside class Mix
        super().YarnInfo()
        print("Acrylic: " + str(self.__Percentage) + "%")

The main program then runs Plain = Yarn("Plain", "Red", 3) and Plain.YarnInfo(). Plain is a Yarn, not a Mix. What is output?

There is no "newest version" across the program. Which version runs depends only on the class of the object it is called on. Plain is a Yarn, so it runs Yarn's method — and a plain yarn does not even have a __Percentage.
Overriding changes what happens for objects of the child class only. The parent class is untouched, so a plain Yarn object still uses Yarn's own method. That is polymorphism working in both directions.
Overriding never edits the parent class. Yarn still has its own YarnInfo; Mix simply has a different one for its own objects.
The parent's method runs normally for parent objects. super() is only how a child reaches the parent's version from inside its own override.

Candidate response 
class Mix(Yarn):
    def __init__(self, Name, Colour, NumberBalls, Percentage):
        self.__Name = Name
        self.__Colour = Colour
        self.__NumberBalls = NumberBalls
        self.__Percentage = Percentage    # INTEGER

    def YarnInfo(self):

        print("Colour: " + self.__Colour)
        print("Acrylic: " + self.__Percentage + "%")
What the examiner says
  • ✓ Class header. class Mix(Yarn): — right relationship, right direction.
  • ✓ Parameters. All four, the parent's three first.
  • ✗ No call to the parent's constructor. The discrete mark is lost. Worse, the three lines that replace it create new attributes that belong to Mix — _Mix__Name and so on. Yarn's attributes are never set, so the first time a parent method runs on a mix — EditNumberBalls(5), say — it crashes with 'Mix' object has no attribute '_Yarn__NumberBalls'.
  • ✓ Percentage is private and its type is evidenced.
  • ✗ The override is re-typed, not extended. It forgets the number of balls, so it no longer outputs "all the information that Yarn outputs".
  • ✗ "Acrylic: " + self.__Percentage joins a string to an integer — TypeError after two lines of output. In Python, build strings with + and str().

What would have scored

class Mix(Yarn):
    def __init__(self, Name, Colour, NumberBalls, Percentage):
        super().__init__(Name, Colour, NumberBalls)
        self.__Percentage = Percentage    # INTEGER

    def YarnInfo(self):
        super().YarnInfo()
        print("Acrylic: " + str(self.__Percentage) + "%")

The habit to build: the moment you type a child's constructor header, the very next line is super().__init__( with the parent's parameters. And when a design says the child outputs "all the information the parent outputs, then…", the override's first line is super(). plus the method's name. Shorter, safer, and it reaches data the child is not allowed to touch.
