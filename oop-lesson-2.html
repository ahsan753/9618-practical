Why a whole lesson on something this small

A get method is two lines long. It is also the single most repeated OOP error in the examiner reports — in all ten of the last ten series. And the idea underneath it, the difference between returning a value and outputting it, is the spine of the whole paper: examiners report marks lost to it in every series, on every question type. Get this right now and it pays on every question you ever write.

Where this sits in the paper

Almost every Paper 4 OOP question asks for at least one get method and one set method, usually straight after the constructor. They are among the cheapest marks on the paper — and among the most often dropped, because candidates write them from a half-remembered pattern instead of from the rule.

Vocabulary

Key terms — learn these wordings

Written the way a mark scheme writes them. Learn the wording, not the gist.

TermDefinition that earns the mark
Get method
(getter, accessor)		A method that returns the value of a private attribute, without changing it.
Set method
(setter, mutator)		A method that takes a parameter and uses it to assign a new value to a private attribute.
ReturnTo pass a value back to the point in the program from which the function or method was called.
OutputTo display a value, for example on the screen with print. Outputting a value does not return it.
EncapsulationAttributes are declared private so they can only be accessed through the class's own methods. Get and set methods are those methods.

What will not earn the mark

"A getter gets the attribute" — no mark; it repeats the word it is defining. "Return means show the answer" — no mark; that is outputting. "A setter changes an attribute" — incomplete; say it takes a parameter and assigns it.

PRIMM · Step 3

Investigate — return, output, get, set

1. The question tells you which one it wants

Before you write a method, find the verb in the question or the class design. It is an instruction, not a figure of speech.

The design says…So your method…
returns the nameends with return self.__Name. No print anywhere.
outputs / displays the nameuses print. Nothing needs to be returned.
returns TRUE if…, otherwise FALSEreturns a Boolean on every path through the method — not only when the answer is True.

2. A get method — three rules

def GetYear(self):
    return self.__Year
  • No parameter other than self. The object already holds the value; there is nothing to pass in. A get method with a parameter is the most repeated OOP error on Paper 4.
  • One return, of the attribute.
  • Unchanged. No input, no assignment, no print. A get method that also changes the attribute is not a get method.

3. A set method — two rules

def SetYear(self, NewYear):
    self.__Year = NewYear
  • Exactly one parameter after self — the new value. Not input() inside the method: the value arrives through the parameter.
  • Attribute on the left, parameter on the right. NewYear = self.__Year runs without an error and changes nothing. Read every assignment right-to-left: "take NewYear, put it into Year".

4. The two set methods that separate the grades

Paper 4 does not stop at "replace the value". Two variants come up, and they are where the marks spread out.

Add to — the parameter is an amount to add, not the new value:

def AddPoints(self, Amount):
    self.__Points = self.__Points + Amount

Writing self.__Points = Amount here throws away everything the object already had. Read the design: "adds Amount to Points" is not "sets Points to Amount".

Clamp — add, but never go past a limit. The order is everything: add first, then limit, then store.

def AddPoints(self, Amount):
    NewTotal = self.__Points + Amount     # 1. add
    if NewTotal > 100:                    # 2. limit
        NewTotal = 100
    self.__Points = NewTotal              # 3. store

Trace it with Points at 90 and a call of AddPoints(30):

Order usedPoints afterwardsVerdict
Add, then limit, then store100✓ correct
Limit the old value, then add120 — 90 passes the check, then 30 is added✗
Limit the parameter, then add120 — 30 is under 100, so nothing happens✗

Adding straight into the attribute and then correcting it (self.__Points = self.__Points + Amount, then if self.__Points > 100: self.__Points = 100) is also fine — the value left stored is still limited. What matters is that the limit is applied to the new total, after the addition.

Checkpoint 1

The class design says: "GetTitle() returns the title of the book." Which method follows the design?

A get method with a parameter is the single most repeated OOP error in the examiner reports — all ten recent series. The object already holds the title, so there is nothing to pass in. Worse, anyone calling GetTitle() the right way now gets a crash.
No parameter other than self, one return, and the attribute is left unchanged. That is the whole of a get method.
This outputs the title rather than returning it. It looks right on screen, but any code that calls it gets None back. The design says "returns".
This reads input and overwrites the attribute — a get method must leave the attribute exactly as it was. Examiners reject a getter that reads input or assigns.

Model answer — check yours against this
Python — Paper 4 
class Book:
    def __init__(self, Title, Year):
        self.__Title = Title        # STRING
        self.__Year = Year          # INTEGER

    def GetTitle(self):
        return self.__Title

    def GetYear(self):
        return self.__Year

    def SetYear(self, NewYear):
        self.__Year = NewYear

MyBook = Book("Dune", 1956)
MyBook.SetYear(1965)
Published = MyBook.GetYear()
BookAge = 2026 - Published
print(MyBook.GetTitle() + " is " + str(BookAge) + " years old")
  • The value returned by GetYear() is stored in Published and then used. The value returned by GetTitle() is used directly inside the print. Both are fine.
  • str(BookAge) is needed — joining an integer to a string with + crashes. Using commas in print works on screen too, but get into the + and str() habit: examiners flag strings built with commas elsewhere on the paper, where a comma makes a tuple.
  • ShowTitle() has gone. It was never asked for, and a method that nobody calls is just more to go wrong.
Checkpoint 2

An object NewMember has a get method GetName() that returns the member's name. Which line outputs the member's name?

The call is made on the object with dot notation, and the value it returns goes straight into print. Storing it first — Name = NewMember.GetName() then print(Name) — is equally good.
The method runs and returns the name — and then the program throws it away. Nothing is output. Not storing or using a returned value is reported in all ten recent series.
This reaches past the method into a private attribute. It crashes with an AttributeError, and even in a language where it ran, it would defeat the encapsulation the question is testing.
This calls the method as if it were a free-standing procedure. Python crashes with a NameError. Calling methods as free procedures appears in six of the last ten series — methods are always called on an object, with a dot.

The marks

Exam technique — the verb is the instruction

A game stores each player as an object. The design says:

Class design — Player (extract)

MethodDescription
GetHealth()Returns the value of Health.
Heal(Amount)Adds Amount to Health. Health can never be greater than 100; if the new total would be greater than 100, Health is set to 100.

Predict, then reveal. A candidate writes this. Decide what an examiner would credit before you open the answer.

Candidate response 
    def GetHealth(self, Health):
        print(self.__Health)

    def Heal(self, Amount):
        if self.__Health > 100:
            self.__Health = 100
        self.__Health = self.__Health + Amount
What the examiner says

Both methods run. Neither earns full marks.

  • ✗ GetHealth takes a parameter. The most repeated OOP error on the paper. The parameter is never even used.
  • ✗ GetHealth outputs instead of returning. The design says "returns". Any code that calls it gets None.
  • ✓ Heal takes one parameter and adds to Health rather than replacing it. Credited.
  • ✗ Heal limits in the wrong order. It checks the old value, then adds. A player on 90 who heals by 30 ends on 120. The limit mark is lost, even though the candidate clearly knew a limit was needed.
What would have scored 
    def GetHealth(self):
        return self.__Health

    def Heal(self, Amount):
        NewHealth = self.__Health + Amount
        if NewHealth > 100:
            NewHealth = 100
        self.__Health = NewHealth

The habit to build: before you write a method, underline the verb in its description. Returns → return. Outputs → print. Adds → + onto what is already there. Can never be greater than → a limit applied to the new total, after the addition.

Checkpoint 3

The design says: "AddCredits(Amount) adds Amount to Credits. Credits can never be greater than 50." Credits is currently 40. Which method leaves Credits at 50 after AddCredits(25)?

This checks the old value (40, which passes) and then adds 25, leaving 65. The limit has been applied before the addition, so it never catches anything the addition creates.
This limits the parameter, not the total. 25 is under 50, so nothing happens, and Credits ends on 65.
This replaces Credits with 25 instead of adding to it. The limit is in the right place, but the design says "adds", so the 40 credits the member already had are lost.
Add first (65), then limit (50), then store. The limit is applied to the new total, after the addition — the only order that works for every starting value.

Accepted alternatives

  • MP9: adding into the attribute and then correcting it (self.__Credits = self.__Credits + Amount, then if self.__Credits > 50: self.__Credits = 50). The value left stored is limited, so it is credited.
  • MP12: storing the returned values in variables first, or calling the get methods inside the print. Both are accepted.

Not credited, however good the code looks

  • A get method with a parameter — MP1 lost, even if the parameter is never used.
  • A get method that prints instead of returning — MP2 or MP3 lost, and MP12 usually with it.
  • SetAge() that reads input() instead of using its parameter — MP4 and MP5 lost.
  • A limit checked before the addition — MP9 lost, and your screenshot will show 65, so MP14 goes too.
  • Code pasted as an image — no code marks at all.
